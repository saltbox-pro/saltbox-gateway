## Описание

Salt.Box Gateway – компонент платформы Salt.Box, реализующий API Gateway для микросервисной архитектуры. Он обеспечивает маршрутизацию запросов, балансировку нагрузки, health-check сервисов, кэширование, а также централизованное управление доступом на основе политик OPA и системы пермишенов.

Gateway работает поверх FastAPI, интегрируется с Redis для хранения состояния и кэша, а также с OPA, Open Policy Agent, для проверки разрешений.

## Быстрый старт

### 1. Запуск

Gateway запускается как часть **Salt.Box Compose** и не имеет собственного файла Docker Compose. Из каталога `saltbox-compose`:

```bash
sudo ./bin/sb-compose.sh up saltbox-gateway
```

### 2. Переменные окружения

- `GATEWAY_HTTP_PORT` – порт для запуска, по умолчанию `8000`
- `REDIS_URL` – строка подключения к Redis
- `OPA_URL` – адрес OPA сервера
- `PROXY_REQUEST_TIMEOUT` – таймаут для проксируемых запросов

### 3. Основные эндпоинты

- `/api/discovery/health` – проверка живости gateway
- `/api/discovery/config` – текущая конфигурация зарегистрированных сервисов
- `/api/discovery/register` – регистрация сервиса или его инстанса
- `/api/discovery/add-standalone-front` – регистрация самостоятельного frontend-модуля
- `/api/discovery/services` – список зарегистрированных сервисов
- `/api/discovery/services/{service_name}` – данные одного зарегистрированного сервиса
- `/api/discovery/services/{service_name}/toggle` – включение или отключение сервиса
- `/api/discovery/services/{service_name}/change-strategy` – смена стратегии балансировки
- `/api/discovery/unregister/{service_name}` – удаление сервиса
- `/api/discovery/unregister/{service_name}/{instance_id}` – удаление инстанса
- `/api/{service_name}/{path}` – проксирование запроса к сервису
- `/static/{service_name}/{path}` – проксирование статических файлов сервиса
- `/api/permissions/{service_name}` – проверка пермишенов текущего пользователя для сервиса
- `/api/user-settings` – получение и сохранение персональных настроек пользователя

## Архитектура

- **ServiceDAO** – слой доступа к данным о сервисах в Redis

- **AuditEventPublisher** – публикация событий аудита о проксируемых запросах через SDK

## Управление сервисами

- Регистрация, отключение и удаление сервисов и инстансов через API
- Автоматическое обновление состояния через health-check
- Поддержка нескольких инстансов одного сервиса

### Регистрация сервиса в Discovery

Для регистрации нового сервиса, например core, используется механизм Service Discovery.
Сервис при запуске отправляет в gateway через API или напрямую в Redis информацию о себе: имя, endpoints, тип, стратегию балансировки, vendor и другие параметры.
Пример регистрации можно найти в исходном коде core и saltbox-sdk, в функции регистрации модуля discovery_client.

- Если сервис с таким именем ещё не зарегистрирован, он добавляется с одним инстансом.
- Если сервис уже существует, добавляется новый инстанс этого сервиса, либо обновляется текущий инстанс при совпадении id.
- В SDK реализован клиент, который отправляет POST-запрос на `/api/discovery/register` с описанием сервиса и его инстанса.
- При регистрации сервис передаёт gateway полный список своих endpoint-ов с их настройками: политикой доступа OPA, параметрами кэширования `cache_ttl`, partial-query, action и другими.
- После регистрации сервис появляется в списке доступных сервисов gateway и становится доступен для проксирования.
- На основе зарегистрированных endpoint-ов gateway проверяет доступ через OPA и кэширует ответы согласно настройкам каждого endpoint-а.
- Список официальных модулей, доступных для регистрации без дополнительных проверок, включает core, processing, metric, scheduler, inventory, migration, audit и client-toolkit.

## Балансировка нагрузки

Поддерживаются стратегии:
- `rr` – Round Robin
- `wrr` – Weighted Round Robin
- `rand` – Random

Стратегия задаётся для каждого сервиса, можно менять через API.

---

## Кэширование

- Кэшируются только успешные ответы со статусом 200 OK, если endpoint поддерживает TTL.
- Кэш хранится в Redis, namespace `gate_cache`.
- Кэш отключается для Swagger/OpenAPI и приватных эндпоинтов.

---

## Проксирование статических файлов

Для сервисов с настроенным `static_host` запросы к статическим файлам проксируются напрямую.

---

## Аудит

Каждый проксируемый запрос к API, независимо от того, обслуживается ли он напрямую сервисом или отдаётся из кэша, публикует событие доступа к данным через `AuditEventPublisher` из saltbox-sdk. Это позволяет вести единый журнал обращений к данным независимо от того, какой сервис их обрабатывает.

## Авторизация и управление доступом

Salt.Box Gateway реализует централизованную систему управления доступом на основе OPA, Open Policy Agent, и пермишенов, поддерживающую модель ABAC, Attribute-Based Access Control.

### Преимущества решения

- **ABAC:** Доступ определяется на основе атрибутов пользователя, ресурса, действия и сервиса.
- **Гибкость:** Политики сгруппированы по сервисам, например core и scheduler, ресурсам, например tasks, jobs и collections, и действиям, например read, create и list.
- **Масштабируемость:** Легко добавлять новые сервисы, ресурсы, роли и условия.
- **Partial Query:** OPA может возвращать фильтр для ограничения данных на уровне запроса.

### 1. OPA, Open Policy Agent

- Для каждого endpoint-а сервисов задаётся OPA-конфиг: policy, action, partial-query, unknowns.
- Gateway формирует input для OPA из трёх частей: subject, то есть пользователь, action и resource, включающий service, path, query и body.
- OPA возвращает разрешение `allow` и, при partial query, фильтр для ограничения данных.

#### Пример input для OPA:

```json
{
  "subject": {
    "sub": "user_id",
    "email": "user@example.com",
    "roles": ["tasks_admin"]
  },
  "action": {
    "method": "GET",
    "name": "read"
  },
  "resource": {
    "service_name": "core",
    "path": ["tasks", "123"],
    "query_params": {},
    "body": null
  }
}
```

#### Пример политики на Rego:

```rego
package core.tasks.read

import data.utils

default allow := false

allow if utils.base.is_admin
allow if utils.base.is_tasks_admin
allow if utils.conditions.check_user_permissions(
    data.permissions,
    input.resource.service_name,
    "tasks",
    "read",
    input.subject,
    object_from_api
)
```

#### Формат объекта пользователя

```json
"subject": {
    "sub": "26b9a3e6-2e80-40c7-8f84-a993a1282169",
    "email": "master@example.com",
    "email_verified": false,
    "name": "Petr Petrov",
    "roles": [
        "test_common"
    ]
}
```

### 2. Пермишены

- На текущий момент пермишены хранятся в файле `data.json`, который загружается в OPA.
- В будущих релизах планируется хранение пермишенов в MongoDB, а также полноценный интерфейс для управления пермишенами с фронта: создание, редактирование, удаление и просмотр.
- Это позволит динамически изменять права доступа без перезапуска контейнеров.

#### Пример пермишена

```json
{
    "is_active": true,
    "service": "core",
    "resource": "collections",
    "action": "read",
    "object_conditions": {
        "slug": { "$in": ["linux", "alt"] }
    },
    "subject_type": "user",
    "subject_conditions": {
        "roles": { "$in": ["test_common"] }
    },
    "created": "2024-07-28T12:00:00Z",
    "modified": "2024-07-28T12:00:00Z"
}
```

**Структура пермишена:**
- `is_active`: активен ли пермишен.
- `service`: имя сервиса, например core.
- `resource`: тип ресурса, например collections.
- `action`: действие, например read или create.
- `object_conditions`: условия на объект, например что slug должен входить в список.
- `subject_type`: тип субъекта, обычно `user`.
- `subject_conditions`: условия на пользователя, например его роль.
- `created`, `modified`: даты создания и изменения.

**Формат условий:**
- Условия задаются в виде объектов с операторами `$in`, `$eq`, `$lt` и другими.
- Можно комбинировать условия по разным полям, использовать вложенные `$and`/`$or`.
- Пример `"roles": { "$in": ["test_common"] }` означает, что пользователь должен иметь одну из указанных ролей.
- Пример `"slug": { "$in": ["linux", "alt"] }` означает, что объект должен иметь slug из списка.

### 3. Partial Query

Для списковых и фильтрующих эндпоинтов, например листинга задач или коллекций, OPA не просто возвращает `allow`, а компилирует набор условий, при которых правило `allow` было бы истинным для разных значений ещё неизвестных на момент проверки данных.

- В конфиге endpoint-а задаётся `is_partial: true`, список `unknowns`, то есть частей данных, которые ещё не известны на момент проверки, например `permissions`, и опционально `partial_query`, по умолчанию `allow == true`.
- Gateway отправляет на `/v1/compile` OPA запрос `data.<policy>.<partial_query>` с входными данными и списком `unknowns`.
- OPA возвращает набор частичных запросов `queries`, каждый из которых описывает условие допуска для одной комбинации неизвестных данных.
- Gateway компилирует этот набор в фильтр одного из двух форматов, которые задаются через `query_filter_format`: `mongo`, объект запроса в стиле MongoDB, или `sql`, часть SQL-условия WHERE.
- Если OPA не вернула ни одного запроса, доступ запрещён. Если среди запросов есть пустой, доступ разрешён без ограничений. Иначе доступ разрешён, но только к данным, удовлетворяющим вычисленному фильтру.
- Если фильтр вычислен, gateway добавляет его в query-параметр `opa_query` проксируемого запроса в виде JSON. Сервис-получатель сам применяет этот фильтр к своим данным, например объединяя его с собственным запросом к MongoDB.
- Каждая такая проверка публикует событие аудита `permission_check` с решением и признаком того, был ли применён фильтр.

## Обновление политик OPA

- На данный момент политики OPA обновляются вручную: необходимо изменить Rego-файлы и перезапустить контейнер OPA для применения изменений.
- В дальнейших релизах политики будут распространяться через OPA Bundles и храниться в Git. При пуше в мастер будет запускаться CI, собираться свежий bundle и автоматически распространяться на все инстансы OPA.
